# Migration 0.15.1 to 0.16.0

Version 0.16.0 changes which of Claude Code's permission prompts the gates cause, and adds a list of commands that are refused in every mode:

- **Notice runs without a prompt.** The notice tier means "say it in one line, then act": the line is not an OK, so a prompt was a second gate. A group of rules that the gates leave free or notice now goes to `permissions.allow`, as free ones did. The hq's own commit and push (`hq-commit`) and the push of a work branch (`push-non-deploy-branch`) therefore stop prompting, and so do merges on repos that are not protected when `merge` is `free` or `notice`. An action in the ok tier still always asks, in every mode, and so does every write on a protected repo and every write on GitHub that a rule cannot hold to one repo (issues, comments, pull requests, Project items).
- **Pushes.** The rule `Bash(git push *)` leaves `ask`: it would override the new allow rules (in `allow`, or in `.claude/settings.local.json`, it may be your own rule, so it is left alone and you get a warning). Two exact forms are allowed, `git push origin HEAD` and `git push -u origin HEAD`, which push the current branch to its origin. A bare `git push` and `git push origin` are not allowed: what they push depends on `push.default` and `remote.origin.push`, and could be more than the current branch, or a `+` refspec, which is a force push. Every other form has no rule, so Claude Code asks. A rule cannot see the branch or the repo: a push from a product repo checkout that deploys on push is `deploy` by the gates and the gates still bind the agents. When any item of `repos:` has `protected: true`, the two push rules go to `ask` instead, the hq's own push included: a push carries no repo name, so a rule cannot tell a push to a protected repo from a push to the hq. A repo that is not registered counts as protected in the gates but does not trigger this. An org that wants a prompt for every push in any case moves `push-non-deploy-branch` and `hq-commit` to `ok` in `org.yaml` (through a decision).
- **Merges and `gh api`.** `Bash(gh pr merge -R <slug> *)` is allowed for each registered repo that is not protected, by exact slug, and `Bash(gh api *)` is allowed when `research` is free or notice; each only with its guards in `ask` (`--admin`, a second repo in any spelling (`-R x`, `-Rx`, `-R=x`, `--repo`) or a URL for merges; an explicit method or a body option for `gh api`, so a write or a GraphQL query still asks). When `merge` is `ok`, `Bash(gh pr merge *)` stays in `ask` and nothing is allowed.
- **Deny baseline.** Force push, remote branch deletion, history rewrites, `git clean` with force, `gh repo delete`, `gh release delete` and `gh api` DELETE are written to `permissions.deny` in every hq, whatever its gates: Claude Code refuses them in every permission mode, auto mode included. The deny rules also cover a git option before `push` (`git -C repo push --force`, `git -c k=v push -f origin x`, `--delete`) and quoted-colon deletes (`git push origin ':x'`). `git reset --hard` goes to `permissions.ask`, so it never runs without a prompt. Deny rules match the usual spellings only: a backstop, and the gates still bind. The CEO can run any of these in a terminal outside Claude Code.

No schema changes: `org.yaml` stays `org/5` and `company/state.md` stays `state/1`.

Apply the sections below in order. In the hq the template placeholders are already rendered, so each edit names a fragment without placeholders. Where a fragment is not found exactly (the CEO edited that part), do not guess: show the CEO the current text and the intended result, and ask.

## 1. Permission rules

### `.claude/settings.json`

Write the rules again as `${CLAUDE_PLUGIN_ROOT}/gates/permissions.md` says, section "Write the rules", from this hq's `org.yaml`: merged, never replaced; every other key and every rule that is not one of that file's rules stays as it is. Regeneration covers `permissions.allow`, `permissions.ask` and `permissions.deny`. With the rules of 0.15.1 in place and the default gates, the changes are:

- These leave `permissions.ask`: `Bash(git push *)` (from `ask` only; see the warning below), `Bash(gh repo delete *)`, `Bash(gh release delete *)` (the last two move to `deny`), and `Bash(gh api *)`, which moves to `allow` when `research` is `free` or `notice` in this hq's `gates:` (otherwise it is simply no longer asked as a whole, and the guards below ask for writes).
- These join `permissions.allow`: `Bash(git add *)` and `Bash(git commit *)` (when `hq-commit` is `free` or `notice`), `Bash(git push origin HEAD)` and `Bash(git push -u origin HEAD)` (when `hq-commit` and `push-non-deploy-branch` are both `free` or `notice` and no item of `repos:` has `protected: true`; otherwise they go to `ask`), `Bash(gh api *)` (when `research` is `free` or `notice`), and, when `merge` is `free` or `notice`, `Bash(gh pr merge -R <slug> *)` for each registered repo that is not protected, by its exact slug (an owner pattern gets none). With `hq-commit` or `push-non-deploy-branch` in `ok` the rules of those groups go to `ask` instead.
- These join `permissions.ask`: `Bash(gh api *-X*)`, `Bash(gh api *--method*)`, `Bash(gh api -f*)`, `Bash(gh api * -f*)`, `Bash(gh api -F*)`, `Bash(gh api * -F*)`, `Bash(gh api *--field*)`, `Bash(gh api *--raw-field*)`, `Bash(gh api *--input*)`, `Bash(git reset --hard*)` and `Bash(git reset * --hard*)`; and, when `merge` is `free` or `notice`, `Bash(gh pr merge *--admin*)`, `Bash(gh pr merge * -R*)`, `Bash(gh pr merge *--repo*)` and `Bash(gh pr merge *://*)`, plus `Bash(gh pr merge -R <slug> *)` for each protected repo.
- `permissions.deny` gains the 32 rules of the baseline, listed in `gates/permissions.md`, section "Never, in any mode", before any forbidden connector the hq already has. Its other entries stay.

If `permissions.deny` already holds a rule of the baseline, keep it once.

Read `.claude/settings.local.json` if it exists (read only; it is never written), and the `allow` list of `.claude/settings.json`. ## 2. Plugin-only changes (no hq edit)

- `hq-version` and `product-repos` now push with `git push origin HEAD`, which no longer prompts. The skills that commit to the hq (`intake`, `record-decision`, `weekly-brief`, `initiatives`) follow the hq's rule: the commit and push are one `hq-commit` (notice), so after the one line of notice they push with `git push origin HEAD`, and skip the push when the hq has no remote.
- Claude Code asks before every other form of `git push`, and refuses force and delete forms in every mode.

In the summary to the CEO, add two plain lines: the hq's commits and pushes, merges on your own repos and reads through `gh api` no longer prompt (pushes only when no registered repo is protected, otherwise every push asks; merges only when the merge gate is not set to need your OK, and a push from a checkout that deploys is still held by the gates, not by a rule); and force push, deleting a remote branch, rewriting history, `git clean` with force, deleting a repo or a release and a `gh api` DELETE are now refused in every mode, while `git reset --hard` always asks.
