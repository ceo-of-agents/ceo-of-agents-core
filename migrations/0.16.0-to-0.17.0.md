# Migration 0.16.0 to 0.17.0

Version 0.17.0 bundles five changes:

- **The user's profile.** A new optional key, `ceo.profile` (`technical` or `non-technical`), set by one plain setup question. With `non-technical`, the chief of staff (CoS) and the departments use plain words in chat: a commit is "saved", a push is "sent to GitHub", a connector is named by its service, not by its MCP server. GitHub keeps its name, and files keep their usual format. The CEO can change the profile later by asking the CoS. Existing hqs get `technical`, which is how they behave today.
- **Close and reopen an org.** A new optional key, `org.status` (`open` or `closed`), and a new hidden skill, `close-org`. Closing lists what is still open, asks the CEO to confirm and where each item goes, writes a decision record and sets the org read-only. Reopening is a new decision record. Nothing is ever deleted.
- **An optional CEO todo list.** Tasks the CEO owns personally can be tracked as `<ORG_ID>-T<n>` items in an optional `company/todo.md` (`schemas/todo.md`), apart from the pending list. The file is created only when the CEO first asks to track a task.
- **Summaries rewritten, history in a log.** Lines of `company/state.md` and the State and Next step of an initiative page are rewritten to the current fact instead of growing. Their history goes to an append-only `company/log.md` (or `initiatives/<slug>/log.md`), outside the boot set. The skills check sizes before each commit, initiative pages get a 4 KiB budget, and `CLAUDE.md` gets shorter to make room.
- **Setup answers file and dry run** (plugin only). The setup wizard can read all its answers from a file (`schemas/setup-answers.yaml`) and has a dry run. Nothing in an existing hq changes for this.

No schema version changes: `org.yaml` stays `org/5` (`ceo.profile` and `org.status` are optional; absent means `technical` and `open`), and `company/state.md` stays `state/1`. Two new file formats: `todo/1` for the optional `company/todo.md`, and the log format of `schemas/log.md`.

Apply the sections below in order, all in one commit: section 4.3 compares files with their last committed version, so do not commit until the checks at the end have passed. In the hq the template placeholders are already rendered, so each edit names a fragment without placeholders; where a fragment says `<ORG_ID>`, write the hq's `org.id` from `org.yaml`. Where a fragment is not found exactly (the CEO edited that part), do not guess: show the CEO the current text and the intended result, and ask.

## 5. Plugin-only changes (no hq edit)

- Setup: the wizard (`init-fleet`) reads all its answers from a file in the format of `schemas/setup-answers.yaml`, asks only for what is missing or invalid, and has a dry run that renders an hq without git, commits or installs. It also asks the profile question of section 1.
- New hidden skill `close-org`: the close procedure (list, confirm, closing record, `org.status: closed`, commit with notice) and the reopen procedure (reopening record, `org.status: open`).
- `session-start`: in a closed org the status opens with one line (closed since the date of the closing record, read-only, the CEO can say "reopen") and every step that writes or starts work is skipped. For a holding, step 7 now reads `org.purpose` and `org.status` of each company and marks a closed one.
- `intake`: in a closed org it frames and routes no new work and leaves handoff notes unprocessed.
- `record-decision`, `weekly-brief`, `initiatives`, `departments` and `product-repos`: in a closed org they say the org is closed and stop, writing nothing. `hq-version`: the check reports in one line and adds no A item, and Apply stops. Only the Reopen procedure of `close-org` writes in a closed org.
- `portfolio-brief`: reads `org.purpose` and `org.status` (and no other key) of each company; a closed company gets a `closed` mark in its Organizations line and its pending items are left out.
