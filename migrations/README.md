# Migrations

How framework upgrades reach an instance (an org's hq repo).

## Principles

- Instance files record the framework version they were generated from: `framework_version` in `org.yaml` and in the `company/state.md` frontmatter.
- A framework upgrade never overwrites instance files. Updating the plugin changes only the plugin.
- Each upgrade that needs changes to instance files ships as `migrations/<from>-to-<to>.md`, for example `0.1.0-to-0.2.0.md`. It describes an explicit, reviewable diff: which files change, the exact edits, and why.
- The chief of staff (CoS) reads the migration, shows the diff to the CEO, and applies it as a normal hq commit only after the CEO approves. The commit also bumps `framework_version` in `org.yaml` and `state.md`.
- Migrations are applied in order, one version step at a time; none is skipped.
- From `0.7.0`, the CoS checks the version at session start with the hidden `hq-version` procedure and proposes the migrations (an older hq gets the check through `intake`). It still applies them only after the CEO's OK.

## Schema versions

Each schema carries its own version in the file (`state/1`, `org/5`, `portfolio/1`, `policy/1`). A breaking change bumps the number (`state/1` to `state/2`) and ships with a migration. Additive, backward-compatible changes do not bump it.

How long a holding keeps reading the previous schema version of a company `state.md` is an open question (design spec, section 11). Until resolved, a reader should accept the version it knows and report any other as "unreadable schema" rather than guess.

## Unreleased changes

A release can bundle several pull requests, and its version number is known only when the release pull request is opened. So a pull request that needs a migration does not create `<from>-to-<to>.md` itself: it adds a note to `migrations/unreleased/`, named `<issue>-<slug>.md` (for example `57-user-profile.md`). Pull requests then never compete for the same file name and can merge in any order.

A note has the shape of a migration without the version step: a title `# Unreleased: <what>`, what changes and why, the schema line (which schema versions stay or change), the exact edits, the plain summary line for the CEO, and a "Check after applying" section. A plugin-only change still adds a short note, so the release's migration can say what changed.

When release-please opens or updates the release pull request `chore: release X.Y.Z`, the release workflow runs `scripts/fold_migrations.py` on its branch and pushes the result as one commit. The script reads every note in `migrations/unreleased/`, ordered by issue number, and writes `migrations/<previous>-to-X.Y.Z.md`: a title and intro, the schema line, one "Version" section first (`framework_version` in `org.yaml` and `company/state.md`), then the edits of each note as numbered sections, a "Summary for the CEO" and one "Check after applying" that joins the checks of all notes (duplicates removed). It also adds the "Current status" paragraph below and deletes the folded notes. With no notes it writes a version-bump-only migration. The first intro paragraph of a note becomes the status text in the README, so write it as a summary. Where two notes edit the same file, the fold keeps issue order and each note's fragments; check that each is still found when you write the second note. A pull request that adds a note should be a `feat` or `fix`, so release-please updates its pull request. The fold runs again on every release-please update, so to change the generated text, edit the notes on `main`. `python3 scripts/fold_migrations.py --dry-run` previews the result. `scripts/ci/check_migrations.py` lists the notes still waiting, checks that each has the shape the fold needs (title, schema line, plain summary line, "Check after applying" section), and fails on the release pull request until the version's migration file exists.
