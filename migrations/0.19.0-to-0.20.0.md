# Migration 0.19.0 to 0.20.0

Version 0.20.0 bundles two changes:

- **A quiet start for a session renewed in the middle of a chat.** A front end can keep one chat open for the CEO while it renews the Claude session behind it, so that the context does not grow without end. Until now the renewed session ran the full session start (sync, checks, inbox, status, pending list) and interrupted the CEO with a recap nobody asked for. Now, when the session's first message starts with `[ceo-of-agents] Continued session:` (followed by the last chat messages verbatim, a line `--- New message ---` and the new message), the `session-start` skill runs a quiet start: it syncs the hq, reads the boot files and what the recent messages point to, and answers the new message directly. The version check, the policy check and the inbox still run and speak only when something needs the CEO now. A normal session start is unchanged.
- **Parent and child items in the pending list and the todo list.** The pending list ("Waiting on the CEO") and the todo list were flat: they could not show which items belong to the same piece of work, which item blocks another, or when a group is done. Now an item can have child items, one level deep, indented by two spaces under it. A child has its own code, urgency, kind and since date, and the CEO answers it by that code; approving a parent never approves its children. The chief of staff (CoS) carries out a parent's approved action only once all its children are done or dropped. When a parent's own ask is answered first, its line stays as the group's head with the new kind `{wait}` and goes with its last child. A decision can open follow-ups as children of its D line. Summaries count the lines that ask something (`ok`, `do`, `decide`), children included, and list each child after its parent. `company/todo.md` can nest tasks the same way, in `## Open` only.

No schema version changes: `org.yaml` stays `org/5`, `company/state.md` stays `state/1` and `company/todo.md` stays `todo/1`. The second change is additive: a list without children is unchanged. The new `{wait}` kind and the indented child lines are valid only from this version, so the check script of an older plugin reports them. `scripts/check-boot-set.sh` now reports a new group, `pending lines nested wrongly`.

Apply the sections below in order, all in one commit. In the hq the template placeholders are already rendered, so each edit names a fragment without placeholders. Where a fragment is not found exactly (the CEO edited that part), do not guess: show the CEO the current text and the intended result, and ask. If an edit's new text is already present (the hq was partly migrated before, or this is a second run), skip that edit silently, without asking: ask only when neither the old nor the new text is found.

## What this changes (show the CEO before applying)

Files of the hq that change:

- `operating-model.md`: one paragraph at the end of "How to start", and one paragraph in "The pending list and codes".

Files that do not change: every agent file, every charter, `org.yaml` (apart from `framework_version`) and the existing items of the pending list and the todo list.

## 1. `operating-model.md`: a quiet start for a renewed session

Section "How to start" (the last section of the file). At its end, after its last line, add this paragraph, with a blank line before it:

```
A front end that keeps one chat open while it renews the session behind it starts the new session with a first line that begins with `[ceo-of-agents] Continued session:`, then the last messages verbatim and, after a line `--- New message ---`, your new message. The CoS then reads the hq without a recap and answers that message; the full status comes at your next normal start.
```

Plain summary for the CEO: "When an app renews its session in the middle of our chat, I answer your message directly instead of repeating the status."

## 2. `CLAUDE.md`: subtasks in the pending list

Section "The CEO pending list". After the bullet that starts `- Every line carries its kind after the urgency:`, add:

```
- Subtasks: a child item is indented two spaces under its parent, one level deep, with its own code, urgency and kind. Approving a parent never approves its children; once its own ask is answered it turns `{wait}` and goes with its last child (plugin's `schemas/state.md`).
```

## 3. `operating-model.md`: child items

Section "The pending list and codes". After the paragraph that starts `Open work the CoS holds instead of routing it`, add this paragraph, with a blank line before it:

```
An item can have child items, indented under it one level deep: the asks it is made of, or the follow-ups a decision opens. Each child keeps its own code and you answer it by that code; approving a parent never approves its children. A parent stays until its children are done; when its own part is answered first, it shows `{wait}`. Your todo list can nest tasks the same way.
```

## 4. Existing items

Existing items are not regrouped automatically. The CoS may propose grouping related items once, and moves an item under a parent only with the CEO's OK, keeping its code and since date.

Plain summary for the CEO: "Related items in your pending list and todo list can now be grouped under one parent; you still approve each by its own code."

## 5. Plugin-only changes (no hq edit)

- The `session-start` skill runs the quiet start when the first message of a session begins with `[ceo-of-agents] Continued session:`; a normal start is unchanged.
- `scripts/check-boot-set.sh` reports a new group, `pending lines nested wrongly`.
- `schemas/state.md` and `schemas/todo.md` describe child items and the `{wait}` kind; the `intake`, `record-decision` and `weekly-brief` skills follow them.
