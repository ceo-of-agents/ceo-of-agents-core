# Operating model: {{ORG_NAME}}

How the CEO works with this org. Generated by ceo-of-agents {{FRAMEWORK_VERSION}} on {{DATE}}.

## One entry point

The CEO talks to the chief of staff (CoS). The CoS frames, routes, records everything in hq and brings back only what needs the CEO. hq (this repo) is the single source of truth: if it matters, it is written here.

## Roles

| Role | What it does |
|---|---|
| CEO (`{{CEO_ROLE_ID}}`) | Sets direction, answers decision cards, gives the OKs the gates require. |
| CoS ({{COS_DISPLAY_NAME}}) | Single point of contact. Frames, routes, records, challenges. Owns hq. Does no deep execution. |
| Departments | Vertical specialists with a charter, a tool allowlist and a model tier. See `org.yaml` and `departments/`. |
| Workers | Cheaper agents for bulk reading and hands-on work: `reader` (read-only) and `worker` (hands-on), defined in `.claude/agents/`. One model tier below their parent. |

## Talking to departments

The CEO may talk to anyone; everything that matters comes back to hq and the CoS records it.

- **A. Through the CoS.** The CoS briefs the department, checks the result and summarizes.
- **B. Direct message inside the CoS session.** "Pass to <department>: [text]" The CoS forwards verbatim, returns the full answer verbatim, and may add a comment.
- **C. Direct session.** Run `claude --agent <agent>` from the hq folder, where `<agent>` is the department's agent name from the routing table in `CLAUDE.md`: its persona in lowercase (for example `claude --agent mike`), or its id when it has no persona. Inside a session you can also type `@` and pick the agent by that name. The department works on its own model and leaves a handoff in `inbox/` at the end. Decisions taken there become official only when the CoS records them. Strategic or cross-department reasoning goes through the CoS. Agents are defined inside hq, so `--agent` works only from inside this folder.

## Rhythms (on demand only)

No scheduled automation, no hooks. Nothing runs unless the CEO opens a session.

| Rhythm | What | How |
|---|---|---|
| Weekly brief | What changed, numbers, decisions needed, and a cleanup check that proposes what to archive | The CEO asks for a brief; the CoS runs its `weekly-brief` procedure and writes `company/briefs/YYYY-MM-DD-weekly.md`. |
| Batched approvals | Several OKs in one pass | Departments prepare, the CoS lists the codes in "Waiting on the CEO", the CEO approves by code. |
| Review | Risks, metrics trend, charters | On request. |

## How decisions flow

1. A question needing the CEO becomes a **decision card** in `company/decision-queue.md` with its own code `{{ORG_ID}}-D<n>`: context, options, recommendation, and exactly one of `proposed_by: <dept-id|cos>` or `needs analysis by: <dept-id>`.
2. The card is listed in "Waiting on the CEO" in `company/state.md`.
3. The CEO answers (in chat, by code).
4. The CoS runs `record-decision`: a numbered, immutable record in `decisions/`, an index row, the card removed, state updated.

To change a decision, a new record supersedes the old one; only the old record's status line changes.

## How approvals work

Gates live in `org.yaml` and are summarized in `CLAUDE.md`. Three tiers: free (do it, mention it), notice (one line before acting), ok (the CEO's explicit OK). The CoS does not ask for OKs the table does not require, batches asks into the pending list, and runs exactly the approved action. The CEO approves by code, for example `{{ORG_ID}}-A2`.

## Permission rules

Claude Code asks before a command unless a rule allows it. `.claude/settings.json` holds rules that follow the gates in `org.yaml`: what the gates leave free or notice runs without a prompt (reading and `gh api` reads, the plugin's own procedures, editing this hq, committing, pushing the current branch to its origin with `git push origin HEAD` or `git push -u origin HEAD` (unless a registered repo is protected: then every push asks, since a rule cannot tell a push to that repo from a push to this hq), and, when `merge` is not in the ok tier, merging on repos that are not protected), except writes on GitHub (issues, comments, pull requests), which always ask because a rule cannot hold them to one repo or to their text; what needs the CEO's OK always asks, in every permission mode (releases, settings, secrets, deletes, a merge when `merge` is in the ok tier, other `gh api` calls that write, and any write on a protected repo). A short list of destructive commands is refused in every mode whatever the gates (force push, deleting a remote branch, rewriting history, `git clean` with force, deleting a repo or a release, a `gh api` DELETE), and `git reset --hard` always asks; you can run them yourself in a terminal outside Claude Code. A stricter gate gives a stricter rule. A rule cannot see the branch or the repo: a push from a checkout that deploys on push is still `deploy` by the gates, and the gates, not the rules, hold there. The CoS writes the rules again when the gates, the repos or the roadmap board change. Rules of your own for this computer go in `.claude/settings.local.json`, which is not tracked; an ask rule from the gates still wins over them. The rules spare prompts; they do not replace the gates.

## The pending list and codes

"Waiting on the CEO" in `company/state.md` is the one list. Actions are `{{ORG_ID}}-A<n>`, decisions are `{{ORG_ID}}-D<n>`. Numbers grow monotonically and are never reused. Each line also says what it needs from the CEO: `{ok}` (approve, then the CoS does it), `{do}` (the CEO does it) or `{decide}` (a decision card).

## Handoffs

A department leaves one file per handoff in `inbox/` (format in `inbox/README.md`). The CoS processes it at the next session start and deletes it in the same commit.

## Working surfaces

Full support: Claude Code on your own machine with the plugin installed for this folder (terminal, the desktop app's Code tab, VS Code, JetBrains through its terminal). Claude Code on the web loads this hq's `CLAUDE.md` and `.claude/agents/` but not the plugin, so the CoS procedures are unavailable there. Chat-only surfaces without repo write access are read-only; their output comes back as files in `inbox/`.

## Plugin requirement

The `ceo-of-agents` plugin must be installed for this hq's folder (`claude plugin install ceo-of-agents@ceo-of-agents --scope project`, run in the folder; repeat it on each computer and after moving the folder). Enabled in `.claude/settings.json` alone, it does not load. `.claude/settings.json` also allows `Skill(ceo-of-agents:*)`, so the procedures run without a prompt, also in non-interactive runs (`claude -p`). Claude Code applies that rule only once the folder is trusted: open it once in an interactive Claude Code session and accept the trust prompt (setup does this for the folder it runs in; a fresh clone needs it once). The CoS procedures (`session-start`, `intake`, `record-decision`, `weekly-brief`, `hq-version`, `departments`, `product-repos`, `initiatives`) come from it. They are hidden from the `/` menu: the CEO never types them, the CoS invokes them.
